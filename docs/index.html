Warrant

Retrieval that respects who's asking

Most RAG systems assume every document is equally readable by every user. That holds for a public docs site, and breaks the moment the same pipeline points at a store where some things are restricted.

Architecture Permission-aware RAG Pre-alpha

The problem

Access control is a retrieval concern

The usual shape is: retrieve the most relevant chunks, then drop the ones the caller isn't allowed to see. It looks correct in a demo and it is wrong in two ways at once.

The security objection is obvious — restricted text has already reached a reranker, a model, and a log line before anything removed it. The quality objection is the one that surprises people, and it is the reason this design exists.

Filter after retrieval and your most access-restricted users get your worst search results. It presents as a relevance complaint. It is an architecture bug.

01 · System

Two paths, one store

Ingest parses documents into structured blocks, chunks them along that structure, and writes each chunk with its access rule copied onto it. Query resolves the caller, turns that into a filter, and applies the filter inside every search leg before anything is scored.

02 · The rule

Clearance AND groups

Two primitives, both opaque to the engine: an optional ordinal clearance tier, and a set of groups. They are combined with AND, and that conjunction is the whole security property.

Allow OR instead and you have rebuilt the most common real-world access bug in this space: a sufficiently senior caller sees everything.

03 · The argument

Why post-filtering fails twice

A reranker needs a deep candidate pool to be worth running. Retrieve a hundred, keep the best ten. Drop unauthorized hits after retrieval and a restricted caller doesn't lose ninety candidates — they lose most of the ones that were ever going to matter.

04 · Write path

Security and consistency are separate problems

When an update narrows a document's access rule, both obvious orderings fail. Write the new chunks then delete the old, and there is a window where the broader rule is still live. Delete first, and the document briefly vanishes.

Typical search stores offer no transaction across a document's chunks, so one atomic mechanism isn't available. The way out is to notice these are two properties with very different costs when violated — and to stop making one mechanism carry both.

05 · Ingest

Stage caches, keyed independently

Each stage caches under a key containing only the configuration that affects that stage. Editing one document reprocesses one document; swapping the context model re-runs enrichment and embedding but not parsing.

Stage Cost Cache key Re-runs when
parse → blocks high content_hash + parser_ver document edited, parser upgraded
blocks → chunks low + chunker_ver …also chunking changed
chunks → context high + context_model …also context model swapped
context → vectors medium + embed_model …also embedding model swapped

One consequence is worth stating out loud: the embedding model is the most expensive decision to reverse. Changing it invalidates every vector with no reuse possible, so it belongs in the config hash — if nothing else, so that a change is detected rather than silently producing a mixed-model index.

06 · Deployment

One stack per team, in their own account

The logical design maps onto AWS without much ceremony. Two placement decisions carry most of the weight: heavy document work runs on Fargate because parsing and enriching a large PDF exceeds a function's duration and image limits, while request-path APIs stay on Lambda so they're cheap and scale to zero. The receiver staying small is what lets ingest back-pressure through the queue instead of dropping events when workers saturate.

The access filter lives inside the OpenSearch query — part of the hybrid request, applied to both the BM25 and k-NN legs before scoring. There is no filtering step after retrieval, which is the whole point of section 03.

Why the reindex path is a state machine

Rebuilding vectors can't take the live index down, so Step Functions drives the sequence: build a timestamped index alongside the live one, fan out one message per document, run the eval suite against the result, and only then swap the alias. The eval gate is the interesting part — the swap is conditional on measurement, which is what makes "retrieval changes ship because numbers improved" an enforced property rather than an intention.
